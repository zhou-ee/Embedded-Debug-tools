二、上一轮已经完成的修改，必须保留

1. 移除生产数据路径中的 TornSampleFilter 自动修复。

原算法会把正常浮点极值误判为撕裂值，并拼接相邻样本的字节来改写数值。例如：
16.18034 → 20.0 → 16.18034
中间的 20.0 会被改成 16.125；真机中还出现过正确负值被改为正值。

已从 AgentService 的示波摄取和 ScopePanel 的 CSV 导出中移除调用。TornSampleFilter 仅保留为历史离线对照工具，不进入生产测量路径。
不要重新引入自动平滑、削峰、插值、位模式重构等方法来掩盖问题。

2. 新增 ScopeSamples，统一保存原始解码值与缺失状态。

缺少目标字节、空字节、长度不匹配时保存 NaN，正常 F32 数据保持原始解码值。
当前超过三个设定采样周期的时间间隔会设置 gapBefore。
绘图先通过 forEachRun 分段，再做段内极值降采样，避免跨缺口连接。
游标不会跨缺口吸附，也不会返回序列范围之外的值。

3. 新增 ScopeCsv，修复导出对齐。

按实际纳秒时间戳合并通道，缺失格子留空，不用最近邻填补其他通道。
处理 CSV 表头转义，保存已采到的真实数值。

4. 修复引擎与 OpenOCD 缺样语义。

Engine 对已返回帧中的每个请求目标都输出对应地址；提取失败时输出空字节。
OpenOCD 整批读取失败仍返回带时间戳的缺样帧，记录后执行 50 ms 避让。
Tcl 传输损坏、失步或连接失败走 ConnectionLost，不能伪装为普通成功读取。
注意：其他整批异常路径及超期漏拍是否仍缺少可观测性，需要继续检查。

5. 修复共享 OpenOCD 会话的清理行为。

新增 DebugBackend.is_shared，OpenOCD 根据实际是否拥有子进程判断共享关系，覆盖 attachOnly=false 但复用已有服务器的情况。
Engine 跟踪自己分配的 DWT 槽位和地址，分配时保留外部占用。
清理前核对 COMP/MASK/FUNCTION，忽略只读状态位；外部改写后的槽位不清除。
Disconnect、连接替换及 Shutdown 使用一致清理路径。
共享目标处于暂停状态时，不自动 resume；不能清空其他调试器的观察点。

6. 修复示波通道的符号和指针绑定。

新增 ScopeTargetResolver。
ELF 重载、重连、恢复采样时重新解析表达式；指针链使用现场读取的指针值，支持嵌套指针和数组。
地址或长度变化时清理对应旧序列；无法定位时暂停该通道并显示“待定位”。
固定地址与 SVD 寄存器通道保留固定绑定，兼容旧持久化配置。
ScopeVariable、持久化设置及 RegisterLiveWatchPanel 已做配套修改。
示波目标下发通过 pushExecutor 串行执行，避免旧地址请求覆盖新地址。

四、后续审查发现的剩余问题

1. 时间戳与实际采集时刻错位。

关键源码：
E:\Software\Develop\Embeded\Clion_plugin\Embedded Debug tools\agent\crates\debug-core\src\probers_backend.rs
E:\Software\Develop\Embeded\Clion_plugin\Embedded Debug tools\agent\crates\debug-core\src\openocd.rs

两个 scope_burst 都在读完所有块后执行 out.push((start.elapsed(), frame))，整个帧共用读取结束时间。回包等待、读取过程及线程调度延迟被混进时间戳，分散地址的多个通道也没有独立采集时序。

直接证据：
E:\Software\Develop\Embeded\Clion_plugin\Embedded Debug tools\tmp\scope-audit-20260930\fixed_ocd_200_user.csv
第 1455—1457 行附近：

相邻帧 Agent 时间戳间隔 56.183 ms，MCU tick 只增加 6 ms；
下一帧时间戳间隔 0.679 ms，MCU tick 却增加 52 ms。
后一对帧的 sin_1hz 从约 15.81 变为 46.61，却被放在仅隔 0.679 ms 的时间位置。

这表明数值和时间标签错位。这里既可能存在实际漏采，也存在缺口位置及大小的失真，必须区分。
不要简单把打点从读取结束移到读取开始，就声称时间准确；应结合采集时间窗、块间时序及目标 tick 验证。

2. 批内使用普通 sleep，超期后追赶旧截止时间。

两个后端都使用：
due = start + interval * (i + 1)
若 now < due，则 thread::sleep(due - now)。

外层 Engine 的粗睡眠与忙等没有覆盖真正的批内采样等待。
超期后循环仍沿用旧截止时间，随后连续快速读取。平均速率可能接近目标，但实际间隔不均匀，错过的历史波形无法通过追赶读取补回。

fixed_ocd_200_user 中的 18 次超过 15 ms 的间隔，全部发生在同一批次内部；该用例每批 8 帧。因此不能仅用批间切换或状态轮询解释这些长间隔。

3. 其他操作占用同一个采样线程。

关键源码：
E:\Software\Develop\Embeded\Clion_plugin\Embedded Debug tools\agent\crates\monitor\src\lib.rs

Engine 主循环依次处理命令、Watch、状态轮询、Scope 和事件推送。
drain_commands 一直处理到队列为空，没有采样预算。
ReadMemSync、Watch、寄存器读取等操作与 Scope 共用后端线程。
状态轮询间隔为 150 ms；probe-rs 每批重新获取 Core。

需要量化这些操作造成的空档，并优化调度和重复读取。可以重构线程或调度，但同一探针、Session、Core 或 Tcl 流的访问仍必须正确串行化，不能引入并发访问冲突。

4. 配置生效与前端判定不同步。

关键源码：
E:\Software\Develop\Embeded\Clion_plugin\Embedded Debug tools\plugin\src\main\kotlin\org\embedded\monitor\agent\AgentService.kt
E:\Software\Develop\Embeded\Clion_plugin\Embedded Debug tools\agent\crates\embedded-clion-agent\src\session.rs

setScopeFreq 先修改前端 currentScopeFreqHz，再通过线程池异步下发；多个请求可能乱序。
set_scope_targets / set_scope_freq 的 RPC 应答只表示入队，不表示 Engine 已执行。
ScopeData 没有配置代次，旧在途帧可能被按新地址或新频率解释。
例如实际后台仍为 200 Hz、前端已按 1000 Hz 判定时，正常约 5 ms 间隔也会触发 3 ms 断线阈值。

考虑串行、原子配置、执行确认或配置代次等机制，防止旧帧被误解释。
同时检查重连续接时间和强制单调时间修正是否掩盖时间问题。

5. 当前断线规则和预热丢弃需要复核。

ScopeSamples 当前按超过三个设定周期断线：
1000 Hz：超过 3 ms；
200 Hz：超过 15 ms。

因此“保留帧都有完整字节”与“没有波形断点”是两件事。
目标或频率真正改变时，rebuild_scope_blocks 仍会丢弃随后 150 ms 的采样。
请定位预热异常来源、评估必要性和替代方案；不要为了消除缺口而放宽阈值、隐藏缺失或输出预热垃圾。

6. 带宽模型与测试验收不足。

bandwidth 模型固定使用 750,000 B/s 和每块 375 字节开销。
用户三个通道的布局为两个读块，在 1000 Hz 会估算出 766,000 B/s 并告警。这个结果不是硬件实测，check_bandwidth 也不执行限速。
应校准估算或修正告警表述，不能据此认定用户已耗尽硬件带宽。

现有 scope_sampling_rate_1khz 测试只要求 1.2 秒至少 700 点，并检查间隔中位数在 0.6—1.8 ms；不检查最坏间隔或时间标签准确性，长空档仍可能通过。
新增有意义的时序回归，覆盖延迟注入、超期处理、配置切换和共享会话行为。
