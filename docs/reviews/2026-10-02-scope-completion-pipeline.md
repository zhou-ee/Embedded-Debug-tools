# 示波空档：完成事件、回调响应与有界采样队列实测

日期：2026-10-02，Asia/Shanghai。生产基线 `0ad35bab05677ef909281c55ed571495f6a18162`，V1.2.36。本轮诊断未修改或安装生产代码，未烧录固件。

## 结论

**确实存在 USB 请求已经完成，而主机尚未处理完成通知的空档。** 本轮用独立线程观察每笔 WinUSB 请求的原生完成事件，捕获到接收事件已经完成、回调仍迟到 53.6912 ms 的实例。此前 ETW 的 ReadyThread/CSwitch 又直接确认了回调线程 Ready 后等待 CPU，以及采样线程被唤醒后等待 CPU 的实例。因此不能把 `read/write` 函数的全部耗时解释成设备传输耗时。

**可以在上一笔完成通知尚未处理时继续发下一条读取指令。** 真机实验已经验证独立发送、预提交接收缓冲和有界 FIFO 请求队列。主动暂停接收线程约 6.6 ms 时，深度 8 的队列继续提交了 6～7 次 RAM 读取，返回的下位机 `uwTick` 逐毫秒递增；深度 1 的同类实验在暂停期间没有提交新读取。期间没有插值或补点。

但是这不等于所有空档都已解决。队列满后仍要停止提交；发送线程、完成处理线程、USB 内核完成路径也会受到调度影响。替换线程池回调、固定分核或增大队列中的任何单一措施，都没有在本轮证明可以消除全部空档。用户提出的主机流水方向可行，收益需要在减少诊断开销后重新验证。

## 如何判定“已完成但未响应”

保留原 nusb 线程池回调，为每个 bulk 请求的 `OVERLAPPED.hEvent` 配置手动复位事件。独立观察线程等待这些事件，与提交、回调进入、通知、API 返回的 QPC 标记逐笔关联。事件句柄跨等待保持存活，并用请求代数防止同一地址/事件复用时错误配对。

系统在异步操作完成时将事件置为有信号；观察线程读到有信号的时间是完成时间的**上界**，包含观察线程自身的唤醒延迟。因此“观察到完成 → 回调进入”的正时间差，是操作完成后仍未进入回调的已证实等待下界。[WinUSB 完成结果说明](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_getoverlappedresult)

不能反过来断言“没观察到早期事件就代表消息没到”。观察线程也可能迟到或被回调先移除登记。另外，普通 IOCP 路径的状态块可能到完成包出队时才更新，所以仅看到 `ERROR_IO_INCOMPLETE` 不能用来排除完成包已经在队列中。[Microsoft IOCP 说明](https://learn.microsoft.com/en-us/windows/win32/fileio/i-o-completion-ports)

这判定的是主机 I/O 完成，不是 USB 包在线路上的精确结束时间；本轮未使用物理 USB 分析仪。

### 接收已完成，回调晚了 53.6912 ms

`trace_observe`，burst 155，USB IN 指针 `2365095442496`：

| 阶段 | 相对 WinUSB 提交开始 |
| --- | ---: |
| 异步提交返回 | 0.0182 ms |
| 独立线程观察到完成事件 | 4.1223 ms |
| 线程池完成回调进入 | 57.8135 ms |

该笔上层 `usb_read` 总计 57.8709 ms。完成已被观察到后，至少 **53.6912 ms** 没有进入回调。不能把这部分归因为“设备还没发送数据”。该事件对应的示波点间隔约 59.0005 ms，数据完整。

这个新窗口没有 ReadyThread，因此 53.6912 ms 不能全部命名为“线程 Ready 后等 CPU”：线程池完成包派发与实际 CPU 排队尚未进一步拆开。之前 ETW 已直接确认回调 Ready 等待 **4.6136 ms**；另一个 USB IN 实例中，UCX 成功完成 24 B 后，到回调进入还有 **1.2592 ms**。

### 回调通知之后，读取仍迟迟不返回

`trace_observe_split`，burst 287，接收指针 `1910566127648`：回调在提交后约 0.1919 ms 已进入，通知标记约 0.1939 ms，上层 API 到约 41.6138 ms 才返回。通知到返回还有 **41.4199 ms**。这定位了完成后的主机恢复区间；缺少该窗口调度记录，不能把它全部断言为 Ready 等待或某个同步锁。

另做取消 bulk IOCP 通知、由专用事件线程直接执行完成通知的实验。该组 bulk 线程池回调计数为 0，仍有空档。最坏实验事件中，完成事件在提交后 0.6812 ms 已被观察，完成通知执行仅 2.5 µs，通知执行结束到读取返回仍约 **1800.2282 ms**。这个异常发生在诊断实验中，未在下面生产控制组出现；其具体抢占、等待或外部暂停原因仍未定，不作为生产代码新增故障结论。

独立事件完成机制使用 `hEvent` 低位禁止该笔操作向完成端口投递，并配对线程池通知计数；每笔完成只由一个线程处理，不提前释放或读取正在传输的缓冲。[Microsoft 接口约定](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-getqueuedcompletionstatus)

### 内核尚未完成，不等于“USB 线上消息没到”

此前 ETW 某笔 16.5462 ms 发送，中断相关事件到 DPC 开始为 **15.5731 ms**，之后 UCX 完成、回调、采样线程才继续。这里用户态替换回调不能直接消除 DPC 开始前的等待。

没有物理分析仪，不能用这个内核区间断言探针晚发包；也不能仅靠给用户采样线程提优先级解决内核 DPC 延迟。现有记录没有确定内部驱动或临界区的原因。

## 提前发送下一条真实 RAM 读取

实验请求把 SELECT、CSW、TAR 和五个 DRW 读取放进一条自包含 `DAP_Transfer`，读取 `uwTick`、三通道浮点波形、`wave_phase`。发送线程按固定 1 ms 网格提交，接收线程处理 FIFO 回复，提前挂接 IN 缓冲，限制未消费请求与 OUT 在途数量。

这和当前 `core.read_32` 的同步路径不同。不能直接让两个线程并发操作同一个 Core：DP/AP 缓存状态、TAR 自动递增和请求/回复匹配会冲突。重复发送当前裸 `TransferBlock` 也可能读到后续地址，不能把它当成下一时刻的同一变量。本实验每条请求重新确定地址，协议失败会停止实验，不把错误数据当样本。

### 人工暂停接收线程验证机制

深度 1 和 8，各 3 s，在收到第 1000、2000 个回复后主动让接收线程睡眠 6 ms。实际暂停约 6.4～6.8 ms：

| 条件 | 第一次暂停期间提交 | 第二次暂停期间提交 | 返回的目标时间 |
| --- | ---: | ---: | --- |
| 深度 1 | 0 | 0 | 无新请求 |
| 深度 8 | 6 | 7 | `uwTick` 连续每次增加 1 ms |

深度 8 第一段目标 tick 为 `1692639..1692644`，第二段为 `1693651..1693657`；`wave_phase` 也随之递增。所有三通道值有效，目标 tick 无倒退。**这明确验证“接收线程尚未响应，另一个线程继续发下一次采样”可行。** 这是人工注入的停顿，不冒充自然故障。

### 自然运行及优先级对照

每组 20 s，同一实验二进制、相同读命令、相同分核：发送 CPU 10、接收 CPU 6、线程池回调等其他线程 CPU 4、事件观察 CPU 8，均位于不同物理 P 核。其 SMT 兄弟和系统 ISR/DPC 没有隔离，所以仍不是系统独占核。AboveNormal 组只给本测试进程线程设置 `THREAD_PRIORITY_ABOVE_NORMAL`，进程保持 Normal，不使用实时优先级。

动态新线程每 100 ms 检查并绑定，起始阶段可能先在其他核运行；这里不宣称整个窗口零迁移。绑定和调度设置只作用于本轮拥有的测试进程。

| --- | ---: | ---: | ---: | ---: | ---: |
| Normal，深度 1 | 895.65 | 3.9994 ms | 61.9994 ms | 207 | 62 ms |
| Normal，深度 8 | 878.15 | 1.0027 ms | 958.1226 ms | 45 | 957 ms |

这里的“提交 Hz”不是生产 UI 示波率；目标 tick 间隔来自真实 RAM 值，有 1 ms 分辨率，跨多个字的读取也不是 MCU 原子快照。各组三通道值有效、目标 tick 无倒退，绑定/设置优先级均无错误。每个条件只有一个短窗口，负载会变化，不据此保证收益。

Normal 深度 8 的最坏区间再次直接确认是**消息已完成，回调迟到**：OUT 完成事件 QPC `11376982054665`，回调 QPC `11376991686374`，相差 **963.1709 ms**；一笔 IN 的对应差为 **963.0114 ms**。两个回调都在 CPU 4，独立事件观察已及时记录完成。队列把 8 个真实样本保存下来，然后达到容量限制而停止提交；第 179～181 个样本的 tick 连续为 `1918131,1918132,1918133`，下一次提交到约 958 ms 后才发生，目标 tick 已为 `1919090`。

因此平均率没有在 Normal 深度 8 组改善，尽管短间隔分布和空档数量改善了。提高优先级与流水结合在后两个窗口改善了结果，但仍有目标采样空档和接收延迟。仅增加队列仍受回调处理、OUT 缓冲回收及响应消费的背压限制。

## 对生产实现的含义

主机端可实施的是：持久端点与缓冲池、提前提交 IN、把定时提交与完成/回复消费分开、有界在途请求、每帧自包含地址状态、验证 FIFO 及错误恢复，再一起评估采样和完成处理线程的调度。只让采样线程换核、提高单个线程优先级、或把阻塞函数写成 `async`，都不等于完成这些改造。

缓冲能跨过有限的接收停顿；主机发送线程或 USB 内核长时间停止推进时仍会耗尽容量。若要求主机停顿期间仍有严格连续的真实采样，需要目标端或具备该能力的探针按时采样并缓存，主机再批量读取。这不是本轮主机流水验证的前置条件，也不否认主机端优化的价值。
