# V1.2.36 示波空档：USB ETW、线程调度与绑核复测

日期：2026-10-02，Asia/Shanghai。基线：`0ad35bab05677ef909281c55ed571495f6a18162`。本轮为真机诊断，未修改生产代码、插件或固件。

## 已确认的原因

偶发空档至少来自三处主机延迟：**xHCI 中断后的 USB 完成 DPC 延迟、WinUSB 完成回调线程等待 CPU、采样线程等待 CPU**。同步读取必须等这些阶段全部完成，期间无法读取下一帧；V1.2.36 的恢复预算和节拍修复无法中断一次已经进入的成功但缓慢的 USB 调用。

这次不再仅把延迟归到 `device.write/read` 调用边界。USB ETW 的 UCX 请求与完成事件，通过同一个 IRP、URB 精确配对；再与 xHCI、DPC/ISR、ReadyThread、CSwitch 和诊断副本的 QPC 标记对齐。多次较长调用中，USB 控制器相关中断很早已出现，DPC 却迟到数毫秒。另一些调用中 USB 内核完成及时，延迟发生在用户线程获得 CPU 之前。

**中断相关事件 → DPC 开始为 15.5731 ms，约占整个调用的 94%。** 之后 UCX 完成到回调进入为 0.5660 ms；回调线程 Ready→运行为 0.5538 ms，采样线程 Ready→运行为 0.3490 ms。回调通知和 API 返回之间也包含极短的代码执行，不能全部命名为 USB 线上传输。

内核 PerfInfo/ISR 与该 xHCI 事件对齐，Wdf01000 ISR 实际约 1.1 µs；USB 完成 DPC 的 Wdf01000 例程约 16.9 µs。CPU 2 在此期间没有记录到一个执行 15 ms 的 DPC，因而不能归因为某个长 DPC 例程一直占住 CPU。另一 NDIS ISR 在 1.6515 ms 出现，其 DPC 也到 15.6168 ms 才执行。DPC/ISR 的起止依据 `InitialTime` 与事件 QPC，Routine 通过 ImageBase/ImageSize 映射模块，参见 [Microsoft DPC 事件说明](https://learn.microsoft.com/en-us/windows/win32/etw/dpc)。

完整 CPU 2 调度记录显示：API 开始前 0.6888 ms 切入 System TID 155976，之后到 API 开始后 16 ms 没有线程切换。这个线程和其他长事件中的 System TID 156960、135180、114440、39832，都从 `ntoskrnl.exe+0x30f900` 开始，基准优先级 12/13。**这些记录定位了 DPC 开始被推迟的区间，尚不能证明该线程内部究竟在哪个驱动调用或临界区停留。** 当前栈记录不足，不据此指认显卡、网卡、探针固件或某个用户应用。

xHCI event 42 没有可读事件名称，本报告依据同控制器字段、相邻 ISR 和 DPC 对应关系称其为“中断相关事件”。此例进入后到 DPC 前只有一个这类事件，DPC 仅处理一个 event。没有 USB 物理分析仪，不能把它的时间直接当作 USB 包在线上的结束时刻。

## 事件 2：USB 已完成，完成回调还在等 CPU

burst 164 的发送 API 耗时 4.6751 ms，而 UCX 请求进入→完成仅 **0.0157 ms**，中断相关事件→DPC 开始仅 0.0009 ms。完成回调线程在 API 开始后 0.0230 ms 已经 Ready，却到 4.6366 ms 才获得 CPU：**Ready 等待 4.6136 ms**。它进入完成回调后很快唤醒采样线程。这一段直接确认是用户线程调度等待，而不是设备用了 4.6 ms 接收数据。

另有 burst 854 的回调 Ready 等待 2.6630 ms，burst 905 为 2.7347 ms。实际回调线程运行优先级为 8，采样线程常为 9；两者均没有设置实时线程优先级。调度事件中同时出现其他应用线程，只能证明竞争上下文，不能仅凭切换前的一个线程名认定它造成了全部等待。

## 事件 3：回调唤醒后，采样线程仍等 CPU

burst 895 发送 API 耗时 3.7696 ms。UCX 请求进入→完成仅 0.0268 ms；回调线程获得 CPU前累计 Ready 等待 1.1842 ms，中途两次被切出。回调在相对 1.2604 ms 唤醒采样线程，采样线程到 3.7506 ms 才重新运行：**Ready 等待 2.4902 ms**。这个事件同时叠加了回调调度和采样线程调度。

burst 854 第 32→33 帧还有另一种等待：读取只用 0.2073 ms，等待下一拍的区间却达 3.8244 ms，比应到时间迟 3.0321 ms，最终点间隔 4.0331 ms。此处不需要长 USB 调用也会产生空档。

正式 1 kHz 窗口的 10 个 >3.001 ms 批内空档，可按主要超期区间分为：5 个 DPC 开始延迟、4 个完成回调/采样线程调度延迟、1 个下一拍等待超期。另一个 3.0593 ms 批间间隔未按帧内方法归因，不与这 10 个混算。

## 为什么上一轮修复后还会出现

[probers_backend.rs](<E:/Software/Develop/Embeded/Clion_plugin/Embedded Debug tools/agent/crates/debug-core/src/probers_backend.rs:391>) 的帧预算控制失败后的恢复动作；首次 `core.read_32` 已经进入时，预算无法取消底层同步等待。读成功、返回完整数据也可以经历上述数毫秒延迟，所以这些事件不会增加重试或降级计数。

底层路径仍为 `read_32 → DAP_Transfer/TransferBlock → bulk 提交 → 等待完成`。Windows nusb 使用 Threadpool I/O 完成回调，再通过 `thread.unpark()` 唤醒等待的采样线程；一次读包含多轮 OUT/IN，因此同时暴露于 DPC、完成回调和采样线程这几个等待点。当前 [main.rs](<E:/Software/Develop/Embeded/Clion_plugin/Embedded Debug tools/agent/crates/embedded-clion-agent/src/main.rs:23>) 已调用 `timeBeginPeriod(1)`，但它不保证线程及时调度，也不能保证 DPC 开始时间。

V1.2.36 跳过超期网格点的处理避免了额外整拍漂移，仍无法补回主机没有读取的采样点。开始读取时的时间戳也只标记样本窗口起点，不能把它解释为 MCU 值被实际读取的精确时刻。带宽和平均采样率有余量，与单次请求的偶发等待同时成立。

## 绑核对照

用户进一步要求用专用核排除频繁迁移影响。本轮采用无需提权的线程亲和性对照，选两个低负载且不同物理 P 核的逻辑处理器：采样 CPU 10（同物理核的 SMT 兄弟 CPU 11），完成回调 CPU 8（兄弟 CPU 9）。测试不更改用户应用或内核线程的亲和性。

测试顺序为不绑核、只绑采样线程、采样/完成回调分核绑定、再不绑核，每组 60 s。各组使用同一个新诊断副本，增加线程当前 CPU 标记，保持 1 kHz、相同读块和正常线程优先级。分核组把测试 Agent 的其余线程放在 CPU 8，记录新线程绑定与错误，并在停止后核对帧和回调标记实际 CPU。

诊断副本 SHA-256 为 `b5e47850b684f1200028ad2ee34294ed52aca4374d2ad962ac62606f4c017e07`，与正式 ETW 窗口副本不同；只在同一副本的四个条件之间比较。空档计数均采用 >3.001 ms：

| 不绑核 1 | 771.44 | 5.9999 ms | 159.9932 ms | 1,542 | 161 |
| 仅采样线程绑 CPU 10 | 829.48 | 5.9999 ms | 52.0332 ms | 1,132 | 183 |

| 不绑核 2 | 762.94 | 6.0001 ms | 49.0017 ms | 1,555 | 195 |

绑定后的标记覆盖预热及正式窗口：仅绑采样组的 50,820 个 `frame_start` 全在 CPU 10；分核组 60,360 个 `frame_start` 全在 CPU 10，247,492 个 USB 完成回调全在 CPU 8，绑定未返回错误。分核组的这两类标记均为零核迁移。不绑核两组，采样线程分别有 18,794、18,174 次相邻帧 CPU 变化，完成回调分别有 56,465、52,117 次相邻同线程回调 CPU 变化；这些只是所记录事件之间的迁移下限，不能当作全部 CSwitch 次数。

**分核绑定确实改善平均采样率与大多数短空档，但零核迁移时仍有空档。** 这排除了核迁移作为全部空档的必要条件。它也说明只绑采样线程不足，应一起考虑完成回调线程；分核组同时把其他 Agent 线程放在 CPU 8、固定使用 P 核，因而不能把改善唯一归因于减少迁移。

分核组最坏事件为 burst 27：发送 142.1023 ms，其中 WinUSB 提交仅 0.0078 ms，完成回调到 142.0347 ms 才进入。另一个 22.1914 ms 的接收事件，回调在开始后 0.0516 ms 已进入、0.0525 ms 已完成通知，API 到 22.1914 ms 才返回；大部分时间发生在通知之后。该阶段的新测试没有 USB ETW / ReadyThread / CSwitch，因此不把前一例未经记录的 142 ms 直接命名为 DPC 延迟，也不把后一例的 22 ms 全部断言为 Ready 状态等待。它们确认了绑核后同步调用仍可能长时间不返回。

随后使用**没有诊断标记的原版生产 Agent**，保留真正的三通道 12 B 读块，再做两组 60 s 对照。通过 Windows `GetThreadDescription` 找到 `monitor-engine`，仅修改本轮测试进程的线程亲和性；全部绑定成功：

| --- | ---: | ---: | ---: | ---: | ---: |
| 不绑核 | 762.41 | 6.0000 ms | 47.2985 ms | 1,453 | 199 |

这两个生产窗口的 >3.001 ms 间隔数量下降约 89.4%，但分核后仍有 154 个，其中 8 个在批间、146 个在批内；均无读取重试、降级、缺字节或时间倒退。生产对照证明本时段的改善并非只存在于加标记的副本。每个条件仅做一个窗口，负载有时变，不把这组比例当作可保证的收益。

后半段不绑核窗口约 762 Hz，与前面正式 USB ETW 窗口约 998 Hz 显著不同；当前记录没有足够信息确认为何系统调度条件改变。不能把跨时段差异直接归因于某次代码修改。CPU 绑核也没有锁定频率，仍可能受电源、热状态、抢占及其他内核活动影响。

亲和性不是系统独占：这些核仍可运行其他进程、ISR/DPC，也存在 SMT 兄弟共享执行资源。[SetThreadAffinityMask](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadaffinitymask) 只限制指定线程允许运行的处理器集合。绑核成功不能单独排除抢占、USB 中断/DPC 延迟或全部调度影响。本轮没有对 USB 中断亲和性、系统启动配置或驱动策略作修改。

当前证据已确认要优化或继续验证的是主机完成与唤醒链路。降低收发轮数、完成等待路径或回调调度可能减少机会，但仅调高采样线程优先级不能直接解决开始前的 DPC 延迟，也不能自动提高完成回调线程优先级。要保证主机暂停期间也有真实连续采样，需要具备目标端定时采样及缓冲的采集方式；这与补绘或伪造时间戳不同。本轮只诊断，未实施这些改动。
